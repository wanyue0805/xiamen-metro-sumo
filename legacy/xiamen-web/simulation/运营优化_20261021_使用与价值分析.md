# 厦门SUMO项目：本轮优化与实际控制价值分析

日期：2026年10月21日。范围：D盘厦门综合交通项目及其网页远程版。

## 核心判断

本项目适合定位为“城市公共交通调度仿真与运行评估平台”。它已经具备读取状态、人工下达控制、推进模型、观察车辆和乘客结果的闭环；本轮增加了评估数据导出。对实际控制最直接的帮助，是在连接真实设备之前验证策略、接口和操作流程，以及用数据比较方案。当前代码没有接入真实列车、现场信号或现场状态采集，不能作为实际地铁行车控制系统。

SUMO的TraCI接口本来就用于读取运行中的仿真对象并改变其行为，因此它适合作为控制程序的虚拟被控对象；这不是现场设备接口。[SUMO TraCI官方说明](https://sumo.dlr.de/docs/TraCI/)

## 本轮完成的改动

1. 修正列车载客数：20人聚合点、5人尾组和1名原始单人乘客，现在显示26人，原先误显示3人。保留原始对象数供核对，未改变物理容量或客流生成方式。
2. 网页显示目标倍率和实际倍率；暂停时实际倍率归零。目标50倍不再等同于已经跑到50倍。
3. 本地和网页增加运行评估：已到达/已出发人数、已完成行程的加权平均全程时间、全程累计候车均值、当前最长连续候车。
4. 按0.5仿真秒分辨率累计待进入、步行、候车、公交内、地铁内时长；暂停不会累积时间。
5. 两端均可导出JSON运行报告，本地另有CSV客流明细，记录参数、时钟、人数、完成情况、时长、端点内部释放偏差及碰撞/瞬移计数。报告不包含账号、设备凭据或本地目录路径。

本地入口位于“客流公交”页的“运行评估”。网页入口位于“运行评估”区域。平均值只统计已完成的聚合乘客，按每组代表人数加权；未完成人数另列。聚合点不是20个独立行人的微观行为。

## 已有能力与实际用途

| 已有能力 | 可以做的实验或演练 | 对控制工作的帮助 |
|---|---|---|
| 五线共用仿真时钟、持续发车和折返 | 线路发车间隔或速度改变后观察服务变化 | 检查多线运行参数与换乘之间的影响 |
| 公交接驳、步行换乘和实际到达 | 固定同一批乘客，对比接驳和轨道设置 | 把“车跑得快”与“乘客到得快”分开评估 |
| 轨道信号红灯保持与恢复自动 | 局部受限、等待、释放后的恢复 | 演练操作顺序，检查控制后的实际模型响应 |
| 列车单车控制和车辆段出入段 | 停车、恢复、回段整备及重新供车 | 检查命令是否产生预期车辆行为 |
| 网页观察、控制权与断线暂停 | 观察者与控制者分离、断线与恢复 | 测试远程调度软件的会话和状态衔接 |
| 新增评估与报告导出 | 保存基准与干预方案结果 | 为方案比较、课程设计、毕业设计和答辩提供证据 |

SUMO支持铁路运行、轨道信号等仿真机制，但具体模型仍需要正确建模。[SUMO铁路仿真说明](https://sumo.dlr.de/docs/Simulation/Railways.html)

SUMO官方会议的研究案例也把它用于数字化铁路控制软件的可视化和自动化测试。这说明“把仿真作为软件测试环境”具有实践价值，但不意味着当前项目已经达到该案例的工程成熟度。[2024年案例：Using SUMO for Test Automation and Demonstration of Digitalized Railway Concepts](https://sumo.dlr.de/pdf/2024/slides6-1.pdf)

## 本次实际做出的方案对照

保持同一批105名模拟乘客、同样4个起终点组合和公交设置，只改变五条地铁线的发车间隔；两组均等到105人全部到达才结束。

| 指标 | 地铁间隔180秒 | 地铁间隔120秒 |
|---|---:|---:|
| 已到达人数 | 105 | 105 |
| 平均全程时间 | 1387.45秒 | 1386.60秒 |
| 平均全程累计候车时间 | 598.90秒 | 598.07秒 |
| 最后一名到达时刻 | 2774.5仿真秒 | 2773.0仿真秒 |
| 碰撞 / 瞬移 | 0 / 0 | 0 / 0 |

本次候车均值只减少约0.83秒，改善很小。它不能证明高峰时加密地铁没有作用；该试验只有一批固定的演示客流，不代表持续高峰需求。它能证明：应该先记录结果，再决定某个参数调整是否有价值。仅凭动画更密集或目标倍率更高，无法判断服务改善。

这组结果也不足以确定瓶颈到底在公交、换乘、折返还是客流时序。下一轮可以分别改变接驳公交间隔、客流到达节奏或限制条件，每次只改变一个因素，比较完成比例、完整行程、候车及车辆投入。应保留相同需求和比较口径。

## 用于实际控制时，目前处于哪一层

### 已经可以做

- 把模拟列车和信号作为虚拟设备，检查一条控制命令能否被执行以及后续影响。
- 设计固定场景，对人工调度或后续算法做重复测试。
- 对比基准方案与调整方案，并保留参数和指标。
- 演示远程观察、控制权争用、状态同步及断线后的处理流程。

### 补齐数据与接口后可以继续做

- 与外部实验控制器、PLC或软件控制器联调，先在台架中验证“输入状态—决策—指令—回执”。当前没有实现这些现场接口。
- 导入真实的时刻表、区间时间、客流和车辆性能数据，校准后为指定场景提供离线运行分析。
- 建立有明确验收条件的受阻恢复和调度算法测试集。

### 目前不支持直接声称的能力

- 直接控制真实地铁列车或现场信号机。
- 准确预测真实厦门某站下一时段的客流或拥挤程度。
- 用示意配线和假设客流得出可直接执行的真实运营方案。
- 宣称已经完成自动最优调度，或具备真实运营数字孪生系统的实时数据闭环。

要走向真实运营分析，我认为应优先补齐与目标场景一致的轨道与区间资料、停站和折返时间、车辆加减速和容量、分时段客流，以及独立的现场数据校核。SUMO官方校准教程也以真实观测与仿真旅行时间的误差来调参数；“地图来自真实地理数据”不能替代运营模型校准。[SUMO校准示例](https://sumo.dlr.de/docs/Tutorials/Calibration/San_Pablo_Dam.html)

## 建议的答辩演示

1. 解释模型范围、示意数据与实际数据来源。
2. 展示基准运行和乘客到达过程。
3. 调整一个控制参数，或保持一个区段红灯。
4. 观察列车及乘客变化，再恢复运行。
5. 导出两份运行报告，比较完整行程、候车和完成人数。

推荐定位表述：

“本项目构建了五线轨道与接驳公交协同运行的仿真环境，支持人工调度干预、乘客换乘、车辆段与信号操作，并通过运行指标和报告导出，对控制策略在给定仿真条件下的效果进行验证。”

## 本轮验证与交付

- 真实混合乘客人数验证：20+5+1=26，7项检查通过。
- 修复前后2400步物理及调度状态摘要一致，未改变位置、速度、停站、折返和客流阶段。
- 真实桌面SUMO和远程libsumo各11项计时检查通过，105人结果一致。
- JSON/CSV真实导出15项检查通过，按人数加权结果一致，无非有限数字和凭据。
- 本地实际按钮、地图切换与缩放检查通过；网页实际倍率、评估、下载、暂停及原有地图操作检查通过。
- 公网静态文件已发布并校验，服务器原服务进程和其他服务保持不变。Windows远程面板已打开并暂停。

本轮没有再次运行120列车8000秒的完整压力测试；它也没有修改上轮的地理定位修复。上述控制价值分析基于当前源码、真实实验及列出的公开技术资料。
